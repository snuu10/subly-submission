# 홈 "나우 로그" 카드 — 우선순위 통합 캐러셀 개편안

> 대상 파일: `components/AiBriefingCard.tsx`, `lib/briefing.ts`, `lib/lifecycle.ts`
> 현재는 앱(mobile)만 대상. 웹 `InsightsWidget.tsx`는 이번 개편 범위 밖(별도 검토 필요).

## 1. 현재 구현과의 차이

사용자가 제안한 5단계 우선순위·자동 전환 규칙을 현재 코드와 대조하면 다음과 같은 차이가 있다.

| 현재 구현 | 제안된 설계 |
|---|---|
| `lifecycle` 종료 알림(`alerts`, 최대 3개)은 캐러셀 **밖**에서 항상 스택으로 표시됨 (`AiBriefingCard.tsx:217-273`) | "구독 종료 확인"이 우선순위 큐 안의 **한 슬롯**(2번)으로 캐러셀에 포함되어야 함 |
| 캐러셀은 슬라이드가 정확히 2개로 고정: ① `fallback`(체험 종료/이번 주 결제/조용함 중 하나, `usageEvent`가 있으면 그 위에 덮어씀) ② `digest`(있을 때만) | 활성화된 후보마다 슬라이드가 되고, 후보 개수는 0~5개로 가변적 |
| `fallback.kind`가 `'this_week'`일 때 "오늘"과 "이번 주"를 한 카드에 합쳐 보여줌(`briefing.ts:96-106`) | "오늘 결제 예정"과 "주간 결제 브리핑"이 서로 다른 우선순위의 별개 카드 |
| 무료 체험 종료 그룹핑(1개면 단독 카드, 2개 이상이면 `이름 · 금액` 2개 + `외 N개`)은 **이미 정확히 그 형태로 구현되어 있음**(`briefing.ts:66-85`) | 제안한 예시(`밀리의서재 · ₩9,900/월`, `외 1개`)와 동일 — 추가 작업 불필요 |
| 자동 전환/스와이프 일시정지/reduce-motion/백그라운드 정지 로직 없음 | 전부 신규 구현 필요 |
| 점 페이지네이션은 `[0, 1]`로 슬라이드 2개 고정 하드코딩(`AiBriefingCard.tsx:380`) | 슬라이드 개수만큼 동적으로 생성 |

즉, "무료 체험 여러 개를 하나로 묶는다"는 요구사항은 이미 만족되어 있고, 나머지는 신규 작업이다.

## 2. 제안 검토

제안하신 자동 전환 규칙(1개면 정지 / 2개 이상 7초 전환 / 터치·스와이프 시 일시정지 / 백그라운드 정지 / 마지막→첫 순환 / 점 또는 N/M 표시 / reduce-motion 시 비활성화)은 모바일 캐러셀 UX의 표준에 부합하고 그대로 채택하는 게 맞다고 판단했다. 다음은 검토 중 추가로 필요하다고 판단한 부분이다.

### 동의하고 그대로 채택
- 좌우 스와이프 필수 + 자동 전환은 보조 기능으로 취급하는 방향
- **7초 고정, 5초 예외 두지 않음**을 추천한다. 카드 본문은 이미 `numberOfLines={2}`로 잘려 있어 줄 수 차이로 체감 읽기 시간이 크게 달라지지 않고, 카드마다 전환 속도가 달라지면 사용자가 리듬을 예측하기 어려워진다. 한 화면 안에서는 항상 같은 간격으로 도는 편이 낫다.
- reduce-motion 시 자동 전환 비활성화. 다만 앱 어디에도 `AccessibilityInfo` 사용례가 아직 없으므로 새로 도입해야 한다(`expo`의 `AccessibilityInfo.isReduceMotionEnabled()` + `AccessibilityInfo.addEventListener('reduceMotionChanged', ...)`).

### 추가로 제안하는 부분

1. **스크린리더 사용 중에도 자동 전환을 멈춰야 한다.** reduce-motion만으로는 VoiceOver/TalkBack 사용자를 다 잡지 못한다. `AccessibilityInfo.isScreenReaderEnabled()`도 함께 확인해서, 둘 중 하나라도 켜져 있으면 자동 전환을 끄는 것을 권장한다.

2. **한 번 스와이프하면 그 화면에 머무는 동안은 다시 자동 전환하지 않는 편이 낫다.** "터치 시 일시정지" 다음에 언제 재개할지가 명시돼 있지 않은데, 몇 초 뒤 재개하면 사용자가 막 읽고 있던 카드가 다시 넘어가 버리는 경험이 될 수 있다. 앱스토어형 캐러셀처럼 "사용자가 한 번이라도 직접 넘기면 이후 자동 전환은 그 컴포넌트가 마운트돼 있는 동안 계속 꺼진 상태로 둔다"를 제안한다.

3. **"구독 종료 확인"을 캐러셀 슬롯 하나로 흡수할 때 그룹핑 규칙이 필요하다.** 현재 `end_confirm` 알림이 여러 개면 카드도 여러 개(최대 3장) 생성되는데, 이걸 우선순위 2번 슬롯 **하나**로 합치려면 체험 종료 카드와 동일한 그룹핑 문구 규칙(`이름 · 금액` 2개 + `외 N개`)을 재사용하는 것을 권장한다. 이미 `resolveBriefing`에 있는 패턴이라 재사용이 자연스럽다.

4. **`ending_soon`(N일 뒤 종료 예정, 아직 확인 불필요) 알림의 자리가 빠져 있다.** 제안하신 5단계 우선순위에는 `end_confirm`(종료됐는지 확인 필요)만 들어있고, `lib/lifecycle.ts`의 또 다른 종류인 `ending_soon`(예: "N일 뒤 끝나요", 해지 안내 버튼만 있음)은 어디에도 속하지 않는다. `ending_soon`을 2번과 합쳐 같은 슬롯으로 취급할지, 아니면 4번(사용 여부 확인)과 5번(주간 브리핑) 사이의 별도 슬롯으로 둘지 결정이 필요하다 — 확정을 위해 아래 질문으로 남겨둔다.

5. **"오늘 결제 예정"이 생기면 기존 `this_week`(이번 주 결제, 오늘 제외) 상태는 설 자리가 없어진다.** 지금 `resolveBriefing`의 `this_week` 분기는 "오늘"과 "이번 주 나머지"를 한 카드로 합쳐서 보여주는데, 새 설계대로 "오늘 결제 예정"이 3번 슬롯으로 독립하면 "이번 주(오늘 제외) 결제 예정"은 5번 "주간 결제 브리핑" 카드가 이미 다루는 정보와 겹친다. 별도 카드로 유지할 필요가 없어 보이므로, `this_week` 분기는 제거하고 그 정보는 주간 브리핑 카드 하나로 흡수하는 것을 권장한다.

6. **5개 후보가 전부 없을 때의 처리(= 기존 `quiet` 상태)가 제안에 빠져 있다.** 카드 자체를 숨길지, 아니면 "이번 주 결제 없어요" 같은 조용한 안내를 마지막 우선순위로 유지할지 결정이 필요하다. 완전히 숨기면 화면이 갑자기 비어 보일 수 있어, **조용한 안내를 6번째(최하위) 카드로 유지하되 다른 후보가 하나라도 있으면 노출하지 않는** 방식을 권장한다.

7. **같은 구독이 여러 우선순위에 동시에 걸릴 수 있다.** 예를 들어 A 구독이 오늘 결제 예정(3번)이면서 동시에 최근 사용 여부 질문(4번) 대상일 수 있다. 이번 설계는 "가장 높은 우선순위 하나만 그 구독에 대해 보여주고, 하위 우선순위 후보군에서는 같은 `subscription_id`를 제외"하는 중복 제거 규칙을 두는 것을 권장한다. 안 그러면 사용자가 같은 구독 이야기를 카드 두 장에서 반복해서 보게 된다.

8. **점 페이지네이션을 슬라이드 개수에 맞게 동적으로 바꿔야 한다.** 지금은 `[0, 1].map(...)`로 2개 고정(`AiBriefingCard.tsx:380`)이라 최대 5개 후보를 지원하려면 `Array.from({ length: slideCount })`로 바꿔야 한다. 점 개수가 3개를 넘어가면 제안하신 대로 "1/3" 같은 숫자 표기 병행도 접근성상 도움이 된다 — 점만으로는 스크린리더가 "선택됨" 상태를 읽어주는 것 외에 전체 개수를 직관적으로 전달하기 어렵다.

## 3. 최종 권장 우선순위 (그룹핑 규칙 포함)

| 순위 | 후보 | 데이터 소스 | 그룹핑 |
|---|---|---|---|
| 1 | 오늘 끝나는 무료 체험 | `resolveBriefing`의 `trial_ending` (기존 로직 그대로 재사용) | 이미 그룹핑됨 (`briefing.ts:66-85`) |
| 2 | 구독 종료 확인(`end_confirm`) — `ending_soon`도 합칠지는 미결정(질문 참고) | `listLifecycleAlerts()` | 동일 그룹핑 문구 규칙 재사용, 중복 제거(1번과 겹치는 구독 제외) |
| 3 | 오늘 결제 예정 | 구독 목록에서 `next_payment_date === today`만 필터링(신규 분기, `this_week` 대체) | 여러 건이면 동일 규칙으로 그룹핑 |
| 4 | 사용 여부 확인 | `selectUsagePromptCandidate('home')` (기존) | 1건만 반환되므로 그룹핑 불필요. 1~3번과 겹치는 구독이면 스킵 |
| 5 | 주간 결제 브리핑 | `fetchWeeklyDigest()` (기존, 월요일에만 생성·화~일은 캐시) | 항상 1건 |
| 6 (최하위) | 조용한 안내("이번 주 결제 없어요") | 기존 `quiet` | 1~5번이 전부 없을 때만 노출 |

## 4. 자동 전환 규칙 (확정)

- 활성 후보 1개: 자동 전환 없음, 점/페이지 표시도 숨김(현재 `digest`가 없을 때 `pagination`을 숨기는 것과 동일한 패턴, `AiBriefingCard.tsx:378`)
- 활성 후보 2개 이상: 7초 간격 자동 전환, 마지막 카드 다음엔 첫 카드로 순환
- 사용자가 터치(스크롤 시작)하면 그 시점부터 컴포넌트가 화면에 떠 있는 동안 자동 전환 영구 정지(재개하지 않음)
- 화면이 백그라운드로 가면(`AppState`, 기존 `app/_layout.tsx`·`lib/notifications.ts`의 패턴 재사용) 타이머 정지, 포그라운드 복귀 시 정지된 채로 유지(자동 재시작하지 않음 — 사용자가 방금 백그라운드로 보냈다는 것 자체가 관심이 없다는 신호이므로)
- `AccessibilityInfo.isReduceMotionEnabled()` 또는 `isScreenReaderEnabled()`가 켜져 있으면 자동 전환 완전 비활성화(스와이프는 항상 가능)
- 페이지 표시: 점(2~3개) / 점 + "N/M" 텍스트 병행(4개 이상) — `accessibilityLabel`에는 항상 "N/M 페이지" 포함

## 5. 결정이 필요한 질문

1. `ending_soon`(아직 확인 불필요, 해지 안내만 있는 알림)을 2번 "구독 종료 확인" 슬롯에 합칠지, 별도 슬롯으로 둘지, 아니면 이번 개편에서 제외하고 다음 배포로 미룰지?
2. 같은 구독이 여러 우선순위 후보에 걸릴 때 상위 우선순위만 남기고 하위는 제외하는 중복 제거 규칙(3장 권장안)에 동의하는지?
3. `this_week`(오늘 제외, 이번 주 나머지 결제) 카드를 제거하고 주간 브리핑 카드로 흡수하는 것에 동의하는지, 아니면 별도로 유지하고 싶은지?

## 6. 구현 시 참고할 기존 패턴

- 그룹핑 문구: `lib/briefing.ts:66-85`의 `trialEndingToday` 처리 로직을 함수로 추출해 재사용
- 백그라운드 감지: `app/_layout.tsx`, `lib/notifications.ts`의 기존 `AppState` 사용례
- 캐러셀 스크롤 제어: 기존 `ScrollView` + `onMomentumScrollEnd`(`AiBriefingCard.tsx:210-213`) 유지, 자동 전환 시엔 `scrollTo({ x: slideWidth * nextIndex, animated: true })` 호출
- 우선순위별 데이터 소스는 이미 각각 존재(`resolveBriefing`, `listLifecycleAlerts`, `selectUsagePromptCandidate`, `fetchWeeklyDigest`) — 새로 만들 것은 "오늘 결제 예정" 필터와, 이 5가지를 우선순위 큐로 합쳐 슬라이드 배열을 만드는 조합 로직뿐
